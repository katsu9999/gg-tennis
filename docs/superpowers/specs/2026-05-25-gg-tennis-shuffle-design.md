## 1. 目的

テニスクラブの集まりで、**会員名簿と当日の出席者・コート数**から、ラウンドごとにランダムかつ公平・新鮮なコート割り振りを自動生成するアプリ。全員がその日なるべく均等に試合でき、**週をまたいでも同じ顔ぶれに偏らない**よう最適化する。屋外・直射日光・サングラス着用でも一目で読めることを最重要とする。

## 2. ユーザーと利用シーン

- **ユーザー**: Golders Green テニスクラブの幹事／参加者。海外駐在員が多く**入れ替わり（帰任）が頻繁**。
- **シーン**: 屋外コート。**基本は週1回開催**（年間およそ50回）。事前に会員名簿を作っておき（一度きり）、当日は「来ている人」をタップで選ぶ → アプリが当日番号 1〜N を割り当て → 「名前→番号」を全員に共有 → 1ラウンドごとに「次のラウンド」で割り振りを更新。スマホは日差しの下、サングラス越しに見る。

## 3. スコープ

### v1 に含む（In）
- **URL一つでクラブ全員アクセス**（iPhone/Android/PC・インストール不要）。**PWA**（ホーム画面追加・オフラインキャッシュ）。
- **クラウド共有**（Supabase）。閲覧=誰でも（URLを知るクラブ全員）、編集=**幹事（admin）のみ**。マジックリンク認証（メール）。
- **オフライン耐性**: 屋外でネット不安定でもローカルキャッシュで操作継続、復帰時に同期。
- **将来セッションとRSVP（出欠事前回答）**: 次回開催日を事前作成し、メンバーの「行く／行かない／未定」を集計。**admin代理入力**＋**公開RSVPリンク**（クラブのLINE/WhatsAppに貼る用URL）の両対応。当日は「行く」と回答した人を**一括で出席化**して既存フローに接続。出席予測でコート数も事前決定可。
- **会員名簿**（名前で永続）。追加・編集・**アーカイブ（帰任）**。
- 当日の**出席選択**＋**ゲスト**（飛び入り）追加。
- **当日番号 1〜N**（毎セッション振り直し・コート表示用）と「名前→番号」一覧。
- コート数（1〜6、既定3）・シングルス許可（既定ON）の設定。
- 基本ダブルス＋端数シングルスで「全員プレー」を最大化。
- 1ラウンドずつ生成。**当日内の試合数・休憩を均等化（公平性）**。
- **跨ぎ＋時間減衰の多様性**（最近の同組・同対戦を週をまたいで回避、古い記録は減衰）。
- セッション内履歴の閲覧＋アプリ再起動時の自動復元。
- **過去セッションの保存・閲覧**（名前付き）。
- **試合結果の記録（任意）**＝勝った側をタップ。**個人ランキング（Eloレーティング）**＋**ペアランキング（勝率）**＋**参加回数ランキング**。**シーズン制（年次リセット）**で当日／今シーズン／過去シーズンを閲覧。
- コートビューUI（枠＋ネット線のミニマル表現）。
- 屋外モード（白基調・高コントラスト・輝度MAX・色に頼らない判別）。
- GG ブランディング（アイコン＝ダーク×ライム、スプラッシュ＝GGのみ）。

### v1 に含まない（Out / 将来）
- 詳細スコア（ゲーム数）入力・得失点ベースのランキング（v1 は勝敗のみ）。
- レベル（実力）を考慮した割り振りバランス調整。
- **v1ではネイティブApp配信なし**（v1.5 で Capacitor で対応）。ただし v1 から **Capacitor互換**で設計（プラグインで置換しやすい抽象化を入れる）。
- 出欠の事前募集・Push 通知。
- 複数クラブ対応（v1 は単一クラブインスタンス）。

## 4. 用語

| 用語 | 意味 |
|---|---|
| 会員（Member） | 名簿上の人。永続の内部ID＋名前を持つ。状態は active / archived（帰任） |
| アーカイブ（帰任） | 会員を非アクティブ化。削除せず履歴を保持。出席候補から外れる |
| 出席者（Attendee） | その日のセッションに参加する会員（＋ゲスト） |
| ゲスト（Guest） | 非会員の飛び入り。その日限りの臨時参加者。名簿・跨ぎ履歴には残さない |
| 当日番号（today-number） | その日の出席者に割り当てる 1〜N の表示用ラベル。毎セッション振り直し |
| セッション | 「その日の集まり」1回分。出席者・全ラウンド・当日統計を保持 |
| ラウンド | 1回分の割り振り（各コートの組＋休憩者） |
| 会場（Venue） | プレーした場所。保存リストから選ぶ／新規追加。セッションに記録 |
| ペア履歴（PairHistory） | 会員ペアの同組・同対戦の**減衰付き重み**。割り振りの多様性に使う。セッションをまたいで永続 |
| 試合結果 | 各マッチの勝者（勝敗のみ）。記録は任意 |
| 試合ログ（MatchLog） | 記録された全マッチ（チーム・勝者）。ランキングはここから算出 |
| Elo | 個人の実力レーティング。勝敗と相手の強さから更新（シーズン内で累積） |
| シーズン | ランキングの集計期間（既定=暦年）。年次でリセットし、過去シーズンは閲覧可 |
| 将来セッション（Planned Session） | 開催前に事前作成されたセッション。日付・会場・コート数候補を持ち、RSVPを集める。当日 `ongoing` に昇格 |
| セッション状態（status） | `planned`（未開催・RSVP収集中）／ `ongoing`（当日進行中）／ `past`（終了・閲覧用） |
| RSVP | メンバーの出欠回答（`going` / `not_going` / `maybe`）。任意のメモ付き |
| 公開RSVPリンク | 認証なしで開けるRSVP回答URL（トークン付き）。クラブのチャットに貼る用 |

## 5. 機能要件

### 名簿
1. **名簿管理**: 会員の追加・名前編集・**アーカイブ/復帰**。検索。アーカイブ済みは別表示。事前に**まとめて追加**（名前を改行で貼り付けて一括登録）も可能。名簿は一度作れば永続保存され、毎セッション再利用する。

### 将来セッション・RSVP
2a. **将来セッション作成（admin）**: 「次の土曜 9:00 @ Golders Hill」のように日付・会場・コート数（暫定）・シングルス許可を事前設定し `status=planned` で保存。
2b. **RSVP管理（admin）**: 名簿一覧から各会員の出欠を **行く / 行かない / 未定** で代理入力。メモ欄あり（「30分遅れる」等）。**状態別グルーピング表示**：行く（◯人の**名前一覧**）／未定（◯人）／行かない（◯人）／未回答（◯人）。サマリも併記（出席予測=◯人 → コート数◯面推奨）。
2c. **公開RSVPリンク（任意）**: 将来セッションごとに**トークン付きURL**を生成しコピー。クラブのLINE/WhatsAppに貼ると、誰でも開いて**名簿から自分の名前を選び**「行く／行かない／未定」を回答可。なりすまし軽減のため、回答端末に LocalStorage トークンを発行し**自分の回答だけ修正可能**（完全な認証ベースは v1.5）。
2c-i. **公開ページでも「行く人リスト」を表示**: 「行く（9人）: 佐藤・山本・田中…」を回答前後ともに表示（*友達が行くなら自分も行く*の効果）。プライバシー配慮として、admin が将来セッション設定で「公開リスト非表示」を選択可（既定=表示）。「行かない／未定」は admin のみ閲覧（公開ページでは人数のみ）。
2d. **当日昇格**: 開催日に「セッションを開始」→ `status=ongoing` に昇格。**「行く」のRSVP者を一括で出席に変換**し、既存の出席選択画面に接続（admin はそのまま追加・削除・ゲスト追加・コート数調整可）。
2e. **ホーム画面のリマインド**: 直近の `planned` セッションをカード表示（日付・会場・**行く人の上位5名チップ＋「+◯人」**・出席予測・公開リンクコピー・「開始」ボタン）。

### セッション開始（当日）
2. **新規セッション（当日即時）**: 将来セッションを使わず即開催する場合のルート。出席者を名簿からタップで複数選択。ゲストを追加可。コート数（既定3）・シングルス許可（既定ON）に加え、**日付**（既定=今日・変更可）と**会場**（保存済みからクイック選択／新規追加）を設定。
3. **当日番号の付与と共有**: 出席確定で **1〜N をランダム抽選**（じゃんけん風）で割り当て。「シャッフル」で振り直し可。「**名前 → 今日の番号**」一覧を表示（全員が自分の番号を確認）。
4. **自動復元**: 進行中セッションがあれば起動時に「再開／新規」を提示。

### プレー中
5. **ラウンド表示（メイン）**: 現在ラウンドを表示（通常多い1〜3面はスクロールなしで1画面、最大6面対応）。各コートはコート図に**当日番号**を配置。休憩者を表示。
6. **次のラウンド**: タップで次の割り振りを生成・表示。
7. **出席者変更**: ラウンド間で当日の出席者を増減。**帰る人はその当日番号を選んで離脱**（その日の欠番として保持・詰め直さない）。**遅参者は会員選択orゲストで追加**し次の当日番号を採番。次ラウンドから反映。

### 履歴
8. **セッション内履歴**: 現セッションの過去ラウンドを前後に辿って閲覧（**名前付き**表示可）。
9. **過去セッション**: 過去の開催を一覧・閲覧（名前付き）。

### 結果・ランキング
10. **試合結果の記録（任意）**: 各コートで勝った側をタップ。未入力でも運用可（割り振りのみOK）。履歴から後で入力・編集可。
11. **ランキング（シーズン制）**: 個人＝**Eloレーティング**順（勝敗数・試合数・直近変動）。ペア＝**勝率**順（最低試合数しきい値）。**参加回数**＝出席したセッション数順（週1回開催の常連・皆勤が分かる）。表示は**当日／今シーズン／過去シーズン**を切替。**毎年リセット**で全員に再チャンス。過去シーズンの順位は年を選んで閲覧。

### 設定
12. **屋外モード**（既定ON）: 高コントラスト白基調＋特大ナンバー。**端末側で輝度を手動MAX**運用（Webブラウザは画面輝度を制御不可のため、起動時に「明るさをMAXに」のヒント表示）。任意でダークテーマに切替可。
13. **幹事（admin）設定**: 幹事のメールアドレスを追加（マジックリンク送信）。複数admin可。

## 6. 割り振りアルゴリズム（コア）

UI から独立した **純 TypeScript のエンジン**として実装（フレームワーク非依存・完全にユニットテスト可能）。エンジンは**会員ID**（ゲストは一時ID）で動き、当日番号は表示専用。

> **注**: `N` = その日の出席者数。`公平性（試合数・休憩）は当日内`で均等化し、`多様性（ペア・対戦の分散）は跨ぎ＋時間減衰`で最適化する（出席者が日々異なるため、累積試合数の跨ぎ均等化はしない）。

### 6.1 ラウンド容量プランニング（コート構成と休憩人数）

ダブルス優先、端数をシングルスで吸収し、プレー人数を最大化。

```text
planRound(N, C, allowSingles):
  if N < 2: return Error("出席は2人以上")
  maxDoublesCapacity = 4 * C
  if N >= maxDoublesCapacity:
      seated = maxDoublesCapacity; doublesCourts = C; singlesCourts = 0
  else:
      seated        = N - (N % 2)              # 偶数化（奇数なら1人休憩）
      doublesCourts = seated // 4
      remainder     = seated - doublesCourts*4 # 0 or 2
      singlesCourts = (remainder == 2) ? 1 : 0
      if remainder == 2 and not allowSingles:  # シングルス無効なら端数は休憩へ
          singlesCourts = 0; seated -= 2
  resters = N - seated
  return { doublesCourts, singlesCourts, seated, resters }
```

**検証例**: 6人2面→ダブルス1+シングルス1・休憩0／10人3面→ダブルス2+シングルス1・休憩0／11人3面→ダブルス2+シングルス1・休憩1／12人3面→ダブルス3・休憩0。
不変条件: `seated + resters == N`、`doublesCourts + singlesCourts <= C`、ダブルス優先。

### 6.2 休憩者の選定（当日内の公平性）

各出席者の**当日 `playCount`** を保持。休憩 `resters` 人は当日プレー回数が多い順（＝休憩が少ない順）に選ぶ。タイブレーク: ①直前ラウンドで休憩した人を避ける ②ランダム。途中参加者は `playCount=0` で優先プレー。
目標不変条件: 任意時点で当日の `max(playCount) - min(playCount) <= 1`。

### 6.3 組み合わせの生成（跨ぎ＋時間減衰の多様性）

会員ペアごとに**減衰付き重み**を永続保持：

- `partnerW[a][b]`: a と b が同チームになった重み
- `opponentW[a][b]`: a と b が対戦した重み
- `sameSessionPartner[a][b] / sameSessionOpp[a][b]`: 当日中の回数（同日repeatを最強に回避）

ランダム貪欲法（小規模 N に十分）：

```text
buildRound(seated, doublesCourts, singlesCourts, hist, sameSession):
  best=null; bestScore=+inf
  repeat K times (例 K=300):
     s = shuffle(seated)
     courts=[]; idx=0
     for _ in 1..doublesCourts:
        four=s[idx..idx+4]; idx+=4
        (A,B)=bestSplit(four, hist, sameSession)   # 2-2の3通りから同組ペナルティ最小
        courts.add(Doubles(A,B))
     for _ in 1..singlesCourts:
        two=s[idx..idx+2]; idx+=2; courts.add(Singles(two[0],two[1]))
     sc = score(courts, hist, sameSession)
     if sc < bestScore: best=courts; bestScore=sc
  return best

score(courts, hist, sameSession):
  s=0
  for court in courts:
     for (p,q) in 同チームの全ペア:
        s += W_PARTNER * hist.partnerW[p][q]
           + SAME_SESSION * sameSession.partner[p][q]
     for (p,q) in 対戦の全ペア:
        s += W_OPP * hist.opponentW[p][q]
           + SAME_SESSION_OPP * sameSession.opp[p][q]
  return s
```

パラメータ初期値（実装時に調整）: `W_PARTNER=3`, `W_OPP=1`, `SAME_SESSION=8`, `SAME_SESSION_OPP=3`, `K=300`。
不変条件: 同日の同組・同対戦は最優先で回避。跨ぎは減衰重みで分散。組が枯渇する小人数では繰り返しを許容し最小ペナルティを採用。

### 6.4 統計更新と減衰

- **ラウンド確定時**: 当日 `playCount/restCount` を更新。同組ペア `partnerW += 1` と `sameSession.partner += 1`、対戦ペア `opponentW += 1` と `sameSession.opp += 1`。
- **新セッション開始時（減衰）**: 永続重みを一律 `*= LAMBDA`（既定 0.7）。`sameSession` はクリア。
  → 直近の組ほど重く、古い組は指数的に薄れる（「古い記録は時間で薄める」）。

### 6.5 試合結果とランキング（Elo・ペア）

- **割り振りの多様性（6.4）と結果記録は独立**。多様性は全ラウンドの組から算出、ランキングは**勝者が入ったマッチのみ**から算出する。
- **試合ログ**に各マッチ（teamA/teamB の会員ID・勝者）を追記。ランキングはログを順に**リプレイ**して算出するため、結果の追加・修正があっても**決定的に再計算**できる。
- **Elo（個人・減衰なし累積）**:
  - 初期レーティング 1500。チームレーティング＝メンバー平均 `R_team = avg(members)`。
  - 期待勝率 `E_A = 1 / (1 + 10^((R_B − R_A) / 400))`、結果 `S_A ∈ {0,1}`。
  - 各メンバー更新 `R += K * (S − E)`（チームAは S=S_A/E=E_A、チームBは S=1−S_A/E=1−E_A）。
  - `K = 24`（最初の約10戦は K=40 の暫定期で早く収束）。シングルスは1人チームで同式。
- **ペアランキング**: 同じ会員ペアが**同チーム**で戦ったマッチの勝率（最低 `MIN_MATCHES = 3`）。上位デュオを表示。
- **参加回数ランキング**: シーズン内に出席したセッション数を会員ごとに集計（各セッションの出席者記録から。試合の有無に依らず「来た＝1」）。
- **シーズン制（年次リセット）**: ランキングは**シーズン（既定=暦年）内のマッチのみ**を対象に算出。試合ログは永続なので、シーズン＝**日付ウィンドウ**としてリプレイするだけ。新シーズンは全員 Elo=1500 から再スタート（みんなに再チャンス）。**過去シーズンも日付範囲のリプレイで再現・閲覧**可。シーズン開始月は設定可（既定=1月）。
- **多様性回避（6.4の減衰重み）はシーズンに依らず連続**（直近の新鮮さ用で、競争順位とは別管理）。
- **ゲスト**: 履歴・試合ログには残すが、v1 のランキング（Elo・ペア勝率）算出からは**除外**。
- パラメータ（`K`・暫定期・`MIN_MATCHES`・シーズン開始月）は調整可。

```text
  showGoingListOnPublic: bool             # 公開ページで「行く人リスト」を表示するか（既定 true）
  createdAt: DateTime
  createdBy: adminId
}

RSVPs: List<RSVP>
RSVP {
  plannedSessionId: String
  memberId: int                           # ゲストはv1のRSVP対象外（当日飛び入りで吸収）
  status: 'going' | 'not_going' | 'maybe'
  note: String?
  updatedAt: DateTime
  updatedBy: 'admin' | 'self_public_link' # 操作ソース（監査用）
  selfToken: String?                      # 公開リンク回答時のLocalStorageトークン（修正権限の検証用・サーバ保存）
}

MatchLog: List<MatchResult>              # 記録された結果（成績ランキングの源泉）
MatchResult {
  sessionId: String, roundIndex: int, courtType: doubles|singles
  teamA: List<memberId>, teamB: List<memberId>
  winner: A | B, at: DateTime
}

RankingStats {                           # シーズン日付窓で、MatchLog（成績）＋セッション記録（参加）から導出
  season: {from:DateTime, to:DateTime}
  elo:    Map<memberId, double>          # シーズン開始時 1500 から
  record: Map<memberId, {win:int, loss:int}>
  pair:   Map<(memberId,memberId), {win:int, loss:int}>
  attendance: Map<memberId, int>         # シーズン内に出席したセッション数
}

Settings {
  seasonStartMonth: int                  # シーズン開始月（既定 1＝暦年）
  outdoorMode: bool                      # 既定 true（前面で輝度MAX）
  darkTheme: bool                        # 既定 false
}
```

### セッション（その日・進行中／過去）
```text
Session {
  id: String
  status: 'ongoing' | 'past'       # planned から昇格して開始（PlannedSession は別エンティティ）
  plannedSessionId: String?        # 元の将来セッション（あれば）
  date: DateTime                   # プレー日（既定=今日・変更可）

  allowSingles: bool               # 既定 true
  attendees: List<Attendee>        # 当日の参加者（会員 or ゲスト）
  nextTodayNumber: int             # 次に採番する当日番号
  rounds: List<Round>

  ref: attendeeRef                 # 会員なら memberId、ゲストなら一時ID

  isGuest: bool
```

## 8. 画面設計

### 8.1 画面一覧とフロー
```text
起動 → (進行中セッションあり?)
          ├ あり → 「再開／新規」
          └ なし → ホーム（次回セッションカード表示）
ホーム ─┬─ 名簿管理（Roster）
        ├─ 将来セッション（RSVP集計・公開リンク）
        ├─ ランキング（個人Elo／ペア勝率／参加回数・シーズン切替）
        ├─ 過去セッション一覧
        └─ セッション開始（将来→昇格 or 即時新規）
              → 出席選択＋設定 → 名前→当日番号 一覧 → ラウンド画面 ⇄ 履歴

公開ルート（認証不要）
/rsvp/:token  ─→  公開RSVP回答ページ（名前選択→行く/行かない/未定）
```
1. **ホーム**: 「セッション開始」「将来セッション」「名簿」「ランキング」「過去セッション」。進行中があれば「再開」。**直近のplanned セッションをカード表示**（日付・会場・行く◯人・公開リンクコピー）。
2. **名簿管理**: 会員一覧（active/archived）、追加・編集・アーカイブ/復帰、検索。
2.5. **将来セッション管理（admin）**: 一覧（日付昇順）。新規作成（日付・会場・暫定コート数）。各セッションでRSVPサマリ、会員ごとの回答編集、公開リンク発行/無効化、当日「セッション開始」ボタン（→ ongoingに昇格）。
2.6. **公開RSVP回答ページ（認証不要）**: クラブのチャットに貼るURL。タイトル（日付・会場）→ **名簿から自分の名前を選択**（active会員のみ）→ 行く/行かない/未定 ＋メモ → 送信。回答後、その端末では「自分の回答」のみ修正可（LocalStorageトークン）。集計（行く◯人）も表示。
3. **出席選択＋設定**: 名簿から出席者を複数選択、ゲスト追加、コート数・シングルス許可、**日付・会場**。将来セッションから来た場合は **RSVP「行く」を初期選択**して表示。
4. **名前→当日番号 一覧**: 割り当て結果を共有（全員が自分の番号を確認）。
5. **ラウンド画面（メイン）**: ヘッダー（GGロゴ小・`R{n}`・`{N}人·{C}コート`）、コートカード×最大6（通常は1〜3面）（横向きコート図・当日番号バッジ・種別タグ）、休憩バー、「次のラウンド →」。各コートで**勝った側をタップして勝敗を記録（任意・後で編集可）**。出席者編集・履歴・リセットへの導線。
6. **履歴**: 現セッションのラウンドを前後ナビ（名前付き表示トグル）。各マッチの結果入力・修正もここから可能。
7. **過去セッション**: 開催日・会場の一覧 → 各セッションのラウンド・結果を閲覧。
8. **ランキング**: タブで個人（Elo順・勝敗数・試合数・直近変動）／ペア（勝率順・最低試合数）／**参加（出席回数順）**。**当日／今シーズン／過去シーズン**を切替（過去シーズンは年を選択して閲覧）。

### 8.2 主要インタラクション
- 次のラウンド: エンジンで生成 → 表示 → 永続化。
- 出席者編集: 「メンバー編集」シートで当日番号チップから離脱者を選択／会員・ゲスト追加。次ラウンドから反映。
- リセット: 確認後、当日セッションを締めて（過去セッションへ保存）新規へ。

## 9. デザインシステム（ビジュアル）

### 9.1 原則：屋外＆サングラスで読める

- 偏光サングラスでの暗転はソフトで完全解消不可 → ヘルプに「端末を90°傾ける」を明記。

## 10. 永続化・同期・自動復元

### 10.1 構成
- **クラウド（Source of truth）**: **Supabase Postgres**。クラブ全体のデータを一元管理（名簿・PairHistory・進行中Session・過去セッション・MatchLog・Settings）。
- **アクセス制御**: Postgres **Row Level Security (RLS)** で「閲覧=public（anon ロール可）／編集=admin（authenticated かつ admin フラグ）」を強制。フロントからは Supabase JS で直接アクセス（バックエンドAPIサーバ不要）。
- **ローカルキャッシュ**: **IndexedDB**（`idb-keyval`）に最新スナップショットを保持。起動時はまずキャッシュを描画→裏で Supabase と同期し差分を反映。
- **リアルタイム同期**: Supabase **Realtime** で他端末の変更を購読（例: 幹事Aがラウンド生成 → 幹事Bの画面が即更新）。

### 10.2 オフライン耐性
- 屋外でネット不安定でも、キャッシュから直近データを表示・操作可。
- 書き込みは **Outbox キュー**（IndexedDB）に追記し、オンライン復帰で順次 Supabase へフラッシュ。
- コンフリクト戦略: v1 は**サーバ最終書き勝ち**（クラブ運用上、複数admin同時編集は稀）。将来は楽観ロックを検討。

### 10.3 自動復元
- 進行中Session は Supabase に常時 upsert（ラウンド生成・結果記録のたび）。
- 起動時に進行中があれば「再開／新規」を提示。新規開始時に PairHistory を減衰。

### 10.4 無料枠の見積り（クラブ規模）
- 会員 ~50人・週1開催 × 年52回 ≈ 年間 ~200ラウンド・~600マッチ → 累計データは数MB級。Supabase 無料枠（500MB DB / 月5GB帯域 / 5万MAU）の **1% 未満**で運用可。

## 12. エッジケース
- **N < 2**: 「出席2人以上」を表示し開始不可。
- **N=2/3**: シングルス1面（3人は1人休憩）。
- **組み合わせ枯渇**（小人数）: 繰り返しを許容し最小ペナルティを採用。クラッシュしない。
- **当日離脱**: その当日番号は欠番として残し詰め直さない。跨ぎ統計は確定済みラウンド分のみ反映。
- **遅参**: 会員選択orゲストで追加、次の当日番号を採番、`playCount=0` で優先。
- **帰任（アーカイブ）**: 名簿から非アクティブ化。履歴・PairHistory は保持。復帰可。
- **ゲスト**: 当日限り。PairHistory（跨ぎ）・ランキングには残さない。任意で「名簿に追加」可（v1は任意・既定しない）。
- **シングルス無効**: 端数2人は休憩へ。
- **名簿が空（初回）**: 出席選択前に会員追加へ誘導（ゲストのみでの開催も可）。
- **結果未入力**: ランキングに影響しない。後から履歴で入力・編集でき、編集時はログ再リプレイで再計算。
- **ゲスト関与の試合**: 履歴・試合ログには残すがランキング算出から除外。
- **シーズン境界**: マッチは日付でシーズンに属する。年をまたぐと自動で新シーズン（全員Elo=1500から）。手動リセット不要。
- **シーズン途中の新会員**: そのシーズンの最初の試合からElo=1500で参加。
- **過去シーズン**: 試合ログから日付範囲でリプレイして再現（いつ見ても同じ結果）。
- **オフライン（屋外で電波弱い）**: ローカルキャッシュから読み取り・操作可。書き込みは Outbox に溜め、オンライン復帰で順次反映。
- **未ログイン操作**: 一般メンバーには編集系UI（ラウンド生成・結果記録・名簿編集）を非表示／無効。誤って叩いても RLS で拒否され副作用なし。
- **複数admin同時編集**: Realtime で他端末の変更を受信し画面を最新化。同時上書きはサーバ最終書き勝ち（v1）。
- **マジックリンクが届かない**: フォールバックで「別メールで再送」「コード入力」を提示（Supabase Auth標準）。
- **PWAキャッシュの古さ**: Service Worker は network-first（または stale-while-revalidate）。バージョン文字列を index.html に埋め、変化検知で更新通知。
- **RSVPなしで現地参加**: admin が当日の出席選択画面で会員をタップ追加（既存フロー）。ゲストでも可。RSVP記録は残るが「going」扱いには遡及しない。
- **「行く」と言ったのに来ない**: admin が出席化しないだけ。RSVP は記録として残り、将来「無断欠席が多い人」を把握する材料に（v1では集計しないが、データは残す）。
- **公開リンクで他人になりすまし**: LocalStorageトークンで「自分の回答」のみ修正可能。新規回答は誰でも可（クラブの仲間内なので軽い抑止のみ）。完全防止は v1.5 のメンバー認証で。
- **公開リンクの拡散**: トークンは admin がいつでも無効化（再発行）可。拡散時のリスクはクラブ内の信頼に基づき低いと判断。
- **将来セッションの重複・順序**: 同日複数開催も許可（朝/夕など）。一覧は `date asc`、過去日のplannedは「未消化」として警告表示。
- **RSVP対象**: v1 は **active会員のみ**。ゲストは当日飛び入りでカバー（事前登録なし）。

## 13. テスト戦略（TDD）
- **round_planner**: 多数の (N,C,allowSingles) で `seated+resters==N`、`courts<=C`、ダブルス優先、検証表一致。
- **rester_selector**: 多ラウンドで当日 `max(play)-min(play)<=1`、連続休憩回避。
- **round_builder**: 十分な人数で同日の同組・同対戦が再現しない。シード固定で決定的検証。枯渇時も最小ペナルティ。
- **stats/減衰**: ラウンドで重み加算、セッション開始で `*=LAMBDA`。同日repeatが跨ぎより強く回避されること。
- **ranking/Elo**: 試合ログのリプレイが決定的（同じログ→同じ順位）。勝者は R 増・敗者は R 減。チーム平均・期待値の計算。暫定期 K。ペア勝率の最低試合数。ゲスト除外。結果編集後の再計算一致。
- **repositories**: Supabase 往復一致、IndexedDB キャッシュ整合、**Outbox**（オフライン→オンライン反映の順序保証・冪等性）、自動復元、過去セッション保存、名簿アーカイブ/復帰、試合ログ永続。
- **RLS ポリシー**: anon ロールで書き込み拒否、admin ロールで許可を、ローカル Supabase（または Postgres コンテナ）で検証。
- **Realtime**: 別タブで生成したラウンドを購読タブが受信して画面更新する E2E（最小）。
- **UI コンポーネント（軽め）**: 1〜3コートが1画面に収まる（最大6面対応）、当日番号バッジのコントラスト、勝者ハイライト＋✓、名前トグル、admin/匿名でのUI差分。
- **PWA**: Service Worker キャッシュ戦略の往復、オフライン起動、更新検知。
- **RSVP**: 将来セッション作成→RSVP追加（admin）→公開リンク経由でanon書き込み（自分の回答のみ修正可・他人の回答は拒否）→当日昇格で「going」が初期出席に変換、までの一連を統合テスト。RLS で `selfToken` 検証も併せて検証。
- 目標カバレッジ 80%+（特に engine）。

## 14. 非機能要件
- **屋外可読性**: 端末側で手動輝度MAX運用＋高コントラスト白基調＋特大文字。
- **パフォーマンス**: 「次のラウンド」生成は体感即時（K=300 貪欲法・N≤16 で数〜十数ms想定・TypeScriptでも余裕）。初回ロードは目標 < 2s（GitHub Pages のCDN＋PWAキャッシュ）。
- **オフライン耐性**: ローカルキャッシュ＋Outbox で電波の悪い屋外でも操作継続（書き込みは後で反映）。
- **配布**: URL を共有すれば誰でも開ける（インストール不要）。PWAでホーム画面追加可・全画面アプリ風。
- **コスト**: GitHub Pages＋Supabase 無料枠で完結（クラブ規模で月額0円）。

## 16. 確定事項 / 前提
- **基盤**: フロントエンド = **GitHub Pages**（HTML/TS/Vite・PWA）、バックエンド = **Supabase**（Postgres + Auth + Realtime）。すべて無料枠で運用（クラブ規模で月額0円）。
- **段階リリース**: **v1 = Web/PWA → v1.5 = Capacitor で Android/iOS ネイティブ配信**。同じコードベースを共有し、データも同じ Supabase を共有。Web版は v1.5 以降も維持。
- **Capacitor 互換設計**: v1 から、画面輝度・ストレージ等の Web API を抽象化レイヤ越しに使い、v1.5 でプラグインに差し替えやすくする。
- **配布**: v1 = URL 1本（iPhone/Android/PC）、v1.5 = それに加えて App Store / Google Play。
- **共有モデル**: 閲覧=URLを知る全員（public）、編集=**幹事（admin・複数可）**。Supabase Auth **マジックリンク**＋ Postgres **RLS** で強制。
- **オフライン**: IndexedDB キャッシュ + Outbox 書き込みキューで電波不安定に耐える。
- **将来セッション・RSVP（v1）**: 開催前に「次回」を作成し、admin代理入力＋公開リンクで出欠を集計。当日「行く」を一括出席化。なりすまし軽減はLocalStorageトークン（完全防止は v1.5 のメンバー認証）。
- **画面輝度**: ブラウザ制約で自動MAX不可 → 端末で手動MAX運用 + 高コントラストUIで補完。
- **識別**: 会員名簿（名前で永続）＋帰任はアーカイブ。コート表示は当日番号 1〜N（毎セッション**ランダム抽選**・シャッフル可）。プレイヤーは**当日に出席選択 → 番号を自動抽選**。
- **コート数**: 上限6・既定3。
- **公平性**: 当日内で均等。**多様性**: 跨ぎ＋時間減衰（LAMBDA=0.7 初期値・要調整）。
- **セッション記録**: 日付（既定=今日・変更可）と会場（保存リストからクイック選択／新規追加）を記録。
- **過去セッション**: 日付・会場・名前付きで保存・閲覧。
- **結果・ランキング**: 結果は勝敗のみ（任意・スキップ可）。個人＝Eloレーティング、ペア＝勝率（最低試合数）。ゲストは除外。ランキングは試合ログのリプレイで算出（編集後も再計算可能）。
- **ランキングはシーズン制**: 既定=暦年で年次リセット（全員に再チャンス）。当日／今シーズン／過去シーズンを閲覧。シーズン開始月は設定可。試合ログは永続で、各シーズンは日付ウィンドウのリプレイ。
- **ランキングは3本立て**: 個人（Elo）／ペア（勝率・最低試合数）／参加回数（出席セッション数）。参加回数はセッションの出席記録から集計（週1回開催の常連把握）。
- 乱数アルゴリズムは貪欲法（K回試行）で開始。品質不足なら局所探索等で改良。
- **プライバシー・GDPR**: UK GDPR / EU GDPR 準拠を設計の前提とする（§17）。Supabase は **EU/UK リージョン**（London/Frankfurt）固定、データ最小化、削除・エクスポート機能を v1 に含める。

## 17. プライバシー・GDPR 対応

クラブは UK 拠点・会員は UK / EU 在住の想定。**UK GDPR（Data Protection Act 2018）** と **EU GDPR** の両方を満たす設計とする。50人規模のクラブ運営・低リスク処理だが、設計時点から配慮を組み込む。

### 17.1 処理する個人データ（インベントリ）

| データ | 用途 | 主体 | 保存場所 |
|---|---|---|---|
| 会員名 | クラブ運営・割り振り・履歴・ランキング表示 | 会員 | Supabase（EU/UK）+ 端末 IndexedDB キャッシュ |
| admin メールアドレス | マジックリンク認証 | 幹事のみ | Supabase Auth（EU/UK） |
| RSVP（出欠回答・任意メモ） | 出席集計・コート計画 | 会員 | Supabase（EU/UK） |
| 試合結果（勝敗・チーム編成） | ランキング算出 | 会員 | Supabase（EU/UK） |
| 出席ログ・参加履歴 | 参加回数ランキング・履歴閲覧 | 会員 | Supabase（EU/UK） |
| IPアドレス・User-Agent（一時） | ホスティング運用（GitHub Pages / Supabase 側のログ） | 全アクセス者 | GitHub Pages CDN / Supabase ログ（短期保管） |

- **特別カテゴリーデータ（健康・宗教・政治信条等）は一切扱わない**。
- **ゲスト**は v1 では名前を保存しない（任意・一時表示のみ）。

### 17.2 法的根拠（Lawful Basis）

- 会員データ・試合データ・RSVP：**正当な利益（Legitimate Interest）** — クラブ運営に不可欠な処理。会員は新規登録時に **admin から書面 or 口頭で説明** を受ける運用ルール。
- admin メアド：**契約履行**（クラブ運営者として認証する目的）。
- 必要に応じて会員から **明示的同意** も取得可（プライバシーノーティスに「データ削除を希望する場合」の連絡先を明記）。

### 17.3 データ保管場所（**Supabase は EU/UK リージョン固定**）

- **本番 Supabase プロジェクトのリージョン**: `eu-west-2 (London)` 推奨、または `eu-central-1 (Frankfurt)` / `eu-west-1 (Ireland)`。
- **絶対回避**: US リージョン・Asia リージョン（追加の越境転送対応が必要になる）。
- **GitHub Pages**: 静的ファイル（HTML/JS/CSS）のみ・**個人データを置かない**。Fastly CDN 経由でヨーロッパのエッジから配信される（ただし Fastly は米企業）。GitHub 自体の DPA は Microsoft / GitHub が公開済み。
- **IndexedDB / LocalStorage**: 端末内（会員所有のスマホ・PC）。保管期間はユーザー操作で削除可。

### 17.4 GDPR 権利の実装（v1 で対応）

| 権利 | v1 実装 |
|---|---|
| **アクセス権**（自分のデータを確認） | admin が会員ごとのデータをダッシュボードで閲覧・印刷可能。一般会員からの要請は admin 経由で対応 |
| **訂正権**（誤った情報の修正） | admin が名前・RSVP・試合結果を編集可 |
| **削除権**（"忘れられる権利"） | admin に **「会員をハードデリート」ボタン**を追加（archive ≠ delete を区別）。試合ログ・PairHistory からも削除される。**削除確認モーダル**で誤操作防止 |
| **データポータビリティ** | admin が会員ごとのレコードを **JSON / CSV エクスポート**できる（名前・RSVP履歴・試合履歴） |
| **異議申し立て権** | プライバシーノーティスに admin 連絡先（メアド）を明記 |
| **撤回権** | 削除権で代替（v1 は同意ベースを最小化しているため） |

### 17.5 データ最小化 & 設計上の配慮

- **会員のメアドは集めない**（admin だけ）。連絡は既存の LINE/WhatsApp 等を継続使用。
- **トラッキング・解析ツール禁止**（Google Analytics 等を入れない）。サーバーサイド（Supabase）の基本ログのみ。
- **第三者フォント禁止**（Google Fonts 等は使わず、システムフォントのみ） — 米国転送・第三者データ流れを回避。
- **CDN フォント・画像も self-host**（GitHub Pages 内に置く）。
- **クッキー / ローカルストレージ**: Supabase Auth の token は LocalStorage（"strictly necessary"）。**クッキーバナー不要**（PECR / ePrivacy 上）。同意が必要なトラッキング系を一切使わない方針を維持する限り。
- **ゲスト**: 名前を永続保存しない（v1）。

### 17.6 公開RSVPリンクのプライバシー設計

「行く人リスト」公開のため、URLが意図せず外部流出した場合のリスクを下げる：

- **トークン**: 32文字以上の暗号学的に強いランダム文字列（`crypto.getRandomValues`）。総当たり困難。
- **無効化可**: admin がいつでも token を再発行・旧 URL は即無効。
- **検索エンジン除外**: `<meta name="robots" content="noindex,nofollow">` ＋ レスポンスヘッダ `X-Robots-Tag: noindex`。
- **クラブ規約**: admin は「公開リンクは内輪共有のみ・SNSに転載しない」をルール化（運用面）。
- **会員ごとに「リスト非掲載」フラグ**（v1 で追加検討・既定=掲載）。

### 17.7 第三者処理者（Sub-processors）

| サービス | 役割 | 拠点 | DPA |
|---|---|---|---|
| Supabase | Postgres / Auth / Realtime | EU/UK リージョン選択（データはそこに留まる） | Supabase が GDPR-ready DPA を提供（プロジェクト設定で agree） |
| GitHub Pages | 静的ホスティング | Microsoft / GitHub（CDN 経由でEU配信） | GitHub の GDPR ステートメント・DPA を参照 |

**両者と DPA を成立させたうえで運用**（既存の標準利用規約に含まれる）。

### 17.8 プライバシーノーティス（v1 配信）

設定画面からリンクできる **1ページの平易な日本語＋英語** のノーティスを `/privacy` ルートに配置。記載項目：

1. データ管理者（クラブ名・admin の連絡先）
2. 集めるデータと用途（17.1）
3. 法的根拠（17.2）
4. 保管期間（会員：在籍中＋過去履歴は保持。退会時にハードデリート要請可）
5. 第三者処理者（17.7）
6. データ主体の権利と行使方法（17.4）
7. ICO（UK） / 監督当局への苦情申し立て権
8. 改定日・連絡先

### 17.9 セキュリティ実装

- **HTTPS 強制**: GitHub Pages はデフォルトHTTPS。Supabase 通信も TLS。
- **RLS**: §11.2 の通り、anon ロールは公開リンク経由の限定 RSVP のみ書き込み可。それ以外は admin（authenticated）必須。
- **シークレット管理**: Supabase の `anon key` は公開鍵相当（RLSで守る）。`service_role key` は絶対にクライアントに置かない。GitHub Actions のシークレットで管理。
- **依存パッケージの脆弱性**: `npm audit` を CI で実行。

### 17.10 インシデント対応

- データ侵害発見時、**72時間以内に ICO へ報告**（UK GDPR Art.33）。
- 影響を受ける会員には admin から直接連絡（LINE/WhatsApp 等）。
- 検知のため、Supabase のアクセスログを月1回 admin が確認する運用。
